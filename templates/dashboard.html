Getting Started

System Requirements

  • Python 3.10 or later
  • Supported OS: Windows, Linux, macOS
  • Minimum 512 MB RAM (1 GB recommended for 100+ devices)
  • SQLite (included with Python - no separate database install needed)

Installation

  1. Extract all files into a folder (e.g. C:\netmon\ or /opt/netmon/)
  2. Install dependencies: pip install -r requirements.txt
  3. Edit config.yaml to add your devices
  4. Run: python netmon.py
  5. Open your browser to http://localhost:8080

Running as a Service (Linux)

[Unit]
Description=MyClover.Tech.netmon
After=network.target

[Service]
ExecStart=/usr/bin/python3 /opt/netmon/netmon.py
WorkingDirectory=/opt/netmon
Restart=always
User=netmon

[Install]
WantedBy=multi-user.target

Save this to /etc/systemd/system/netmon.service, then run systemctl enable --now netmon.

Adding & Managing Devices

Adding a Device via Dashboard

  1. Go to the Manage Devices tab
  2. Click Add Device
  3. Fill in: Name, Host/IP, Group (optional), and at least one Check
  4. Click Save

Adding a Device via config.yaml

devices:
  - name: "My Server"
    host: "192.168.1.50"
    group: "Servers"
    parent: ""
    notes: "Production web server"
    maintenance: false
    links: []
    checks:
      - type: ping
        label: "ICMP"
      - type: http
        label: "HTTP"
        url: "http://192.168.1.50"
        expected_code: 200

Status & Monitoring

Status Colors

Check Interval

The default check interval is 60 seconds. Change it in Settings > General or in config.yaml under check_interval_seconds. The dashboard auto-refreshes every 30 seconds.

Thresholds

Each check can have warning_ms and critical_ms thresholds. If response time exceeds the warning threshold, the status becomes WARNING. If it exceeds critical, it becomes CRITICAL.

Device Detail Drawer

Click any device card on the Status tab to open a detail drawer showing uptime percentages (24h/7d/30d), check history, performance charts, links, and notes.

Alerts & Notifications

Email Alerts (SMTP)

Configure SMTP settings in Settings > SMTP or in config.yaml:

smtp:
  smtp_host: "smtp.gmail.com"
  smtp_port: 587
  use_tls: true
  username: "you@gmail.com"
  password: "app-password"
  from_addr: "netmon@yourdomain.com"
  recipients:
    - "admin@yourdomain.com"
  cooldown_minutes: 15

Use the Test Email button in Settings to verify your configuration.

Alert Cooldown

To prevent alert storms, the same device/check will only trigger one email per cooldown period (default 15 minutes).

Acknowledging Alerts

On the Alerts tab, click Ack next to any alert to acknowledge it. Acknowledged alerts stop generating repeat notifications until the device recovers and fails again. Use Ack All to acknowledge everything at once.

Multi-Channel Notifications (Enterprise)

Click Add to Monitoring next to any discovered host to immediately start monitoring it. Discovered devices also appear on the Network Map with dashed borders.

Importing to Inventory

Scan results can be imported into the Asset Inventory with one click.

Host Dependencies (Pro+)

Host dependencies model the physical/logical hierarchy of your network. When a parent device goes down, child devices are automatically marked PARENT DOWN.

How It Works

  1. Set a Parent device when adding or editing a device
  2. If the parent device becomes CRITICAL, all children skip their checks and show PARENT DOWN
  3. This prevents alert storms from cascading failures (e.g. a router outage that takes down all connected servers)
  4. Dependencies are recursive -- if A depends on B and B depends on C, and C goes down, both A and B are marked PARENT DOWN

Visualization

Dependency relationships appear as directed arrows on the Network Map.

Performance Graphing (Pro+)

Every check automatically records response time data. View performance trends by clicking a device card to open the detail drawer.

Time Periods

Select 1 hour, 6 hours, 24 hours, or 7 days. Data is automatically downsampled to max 200 points for performance.

Chart Colors

  • Green data points = OK response times
  • Yellow = WARNING threshold exceeded
  • Red = CRITICAL threshold exceeded
Scheduled Downtime (Pro+)

Scheduling Downtime

  1. Go to the Downtime tab
  2. Click Schedule Downtime
  3. Select a device, set start/end times (UTC), and add a reason
  4. During the downtime window, checks and alerts are suppressed automatically

Downtime States

  • Upcoming: Scheduled but hasn't started yet
  • Active: Currently in progress (checks suppressed)
  • Expired: Completed (can be removed from history)

Cancel any upcoming or active downtime with the Cancel button.

Security Scanner (Enterprise)

The built-in security scanner performs non-destructive, passive analysis of your network devices.

Scan Types

ModuleWhat It Checks
Port Scan33 common ports with banner grabbing and service identification
SSL/TLSCertificate expiry, weak protocols, weak ciphers, untrusted CAs
HTTP Headers7 critical security headers (HSTS, CSP, etc.), server info disclosure
ServicesFTP anonymous login, Telnet, RDP, exposed databases, Redis no-auth, VNC, SMB
SNMPDefault community strings (public, private, etc.)
DNSZone transfer (AXFR) vulnerability

Running a Scan

  1. Go to the Security tab
  2. Optionally enter specific target IPs (leave blank to scan all configured devices)
  3. Select scan types and click Start Scan
  4. Use the Stop Scan button to cancel a running scan

Severity Levels

  • Critical -- Immediate action required (e.g. expired cert, FTP anonymous login, default SNMP)
  • High -- Important fix needed (e.g. missing HSTS, exposed databases, weak SSL)
  • Medium -- Should be addressed (e.g. missing headers, RDP exposed)
  • Low -- Minor informational (e.g. server version disclosed)
  • Info -- Informational only (e.g. open port listing)

All scans are purely passive -- no exploits, no payloads, safe to run on production networks.

users:
  - username: admin
    password: your-strong-password
    role: admin
  - username: operator1
    password: changeme
    role: operator

Authentication is only enforced when users are configured and an Enterprise license is active. Sessions use signed tokens with 24-hour expiry.

SNMP Deep Polling (Enterprise)

Deep-poll SNMP-enabled devices for detailed system metrics.

Metrics Collected

  • CPU load (1-min, 5-min, 15-min)
  • Memory usage (total, used, free)
  • Disk utilization
  • Network interface counters (bytes in/out)
  • System uptime and description

Requirements

Net-SNMP tools must be installed on the netmon server:

  • Ubuntu/Debian: sudo apt install snmp
  • RHEL/CentOS: sudo yum install net-snmp-utils
  • Windows: Download from net-snmp.org

API: GET /api/devices/<name>/snmp

Hot Reload

Most settings changes made via the dashboard or API are applied immediately without restarting netmon. Device changes and SMTP settings are hot-reloaded.

Database

All monitoring data is stored in netmon.db (SQLite) in the same directory as netmon.py. No database server required.

Troubleshooting

Dashboard shows "Loading..." and doesn't update

This usually means the API is unreachable. Check that netmon.py is running and the port (default 8080) is accessible. If you recently upgraded, clear your browser cache (Ctrl+Shift+R).

Port 8080 already in use

Change the port in config.yaml under dashboard: port: or stop the other process using that port.

Ping checks show CRITICAL on Windows

Netmon v4+ validates Windows ping output by checking for TTL in the response. Make sure you're running as a user with permission to execute ping commands.

Email alerts not sending

  • Verify SMTP settings in the Settings tab and use Test Email
  • For Gmail: enable "App Passwords" (not your regular password)
  • For Office 365: use port 587 with TLS enabled
  • Check that recipients is not empty

License key not accepted

Copy your full license key exactly as received, including all dashes. Keys are case-sensitive.

Database errors or corruption

Stop netmon, rename/delete netmon.db, and restart. A fresh database will be created automatically. Note: this resets all history data.

"Permission denied" on Linux

ICMP ping usually requires root or the cap_net_raw capability. Run as root or set: sudo setcap cap_net_raw+ep $(which python3)

Discovery scan finds no hosts

  • Verify the CIDR range is correct for your subnet
  • Some hosts may block ICMP (try with port scanning enabled)
  • Firewalls may block ping between subnets

High CPU usage

Increase check_interval_seconds. Monitoring 100+ devices every 30 seconds can be CPU-intensive. Recommended: 60s for up to 200 devices, 120s for 200+.

SNMP checks failing

  • Ensure net-snmp tools are installed (snmpget --version should work)
  • Verify the community string matches the device configuration
  • Check that SNMP is enabled on the target device and UDP port 161 is open
